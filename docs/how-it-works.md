# How It Works — Plain English

Conceptual walkthroughs of what each service actually does, in plain terms — no code, no framework jargon. For *why* things are built this way, see the Decision Log in `study-hub-architecture.md`. This doc is about *what happens*, not *why we chose it*.

## Auth service

Auth is where accounts live and where you prove who you are.

- **Signing up:** you give it an email and password. It never stores your actual password — it runs it through a slow, one-way scrambling function (Argon2id) and stores only the scrambled result. Even if someone stole the database, they couldn't get your password back out of it.
- **Logging in:** you give your email and password again. Auth scrambles what you typed the same way and compares it to what's stored. If they match, you're you. In exchange, you get two things: a short-lived **access token** (good for 15 minutes) and a longer-lived **refresh token** (good for 30 days). The access token is like a wristband at a venue — show it, get in, no questions asked, but it expires fast. The refresh token is the ticket stub that lets you get a new wristband without buying a new ticket.
- **Using the access token:** any request that needs to prove who you are attaches this token. Auth signs it in a way only Auth's private key could have produced, so anyone holding Auth's *public* key (like Gateway) can check "this really came from Auth, and it hasn't expired" without ever having to ask Auth directly.
- **Refreshing:** when the 15-minute wristband expires, you hand over your refresh token to get a new wristband. Auth also swaps your old refresh token for a brand-new one every time this happens — so if someone ever steals an old, already-used refresh token and tries to use it, Auth notices that token shouldn't exist anymore and treats it as a break-in attempt: it logs you out everywhere as a precaution, not just rejecting that one request.
- **Logging out:** you hand back your refresh token and Auth marks it dead. No more wristbands can be requested with it — but your *current* wristband, if you still have an unexpired one, keeps working until it naturally expires. Logging out kills future refreshes, not an access token already in flight.
- **Authenticating a service instead of a person:** some callers aren't a human at all — a background sync job (Connectors) needs to talk to Items on its own authority, with nobody sitting at a keyboard. For that, Auth hands out a completely different kind of credential up front: a `client_id` and a `client_secret`, generated once and stored by the service that needs it, not typed by anyone. Whenever that service needs to act, it trades its `client_id`/`client_secret` for a short-lived **service token** — same wristband idea as an access token, except this wristband says "this really is Connectors," never "this is user X." Auth tells the two kinds of wristband apart by what's baked into them: a user's wristband carries *who they are*; a service's wristband carries *which service it is*, with no person attached at all.

## Gateway service

Gateway is the one front door everything comes through. It doesn't store anything itself — no database, no accounts — it just decides "is this request allowed?" and hands it off to whichever real service does the actual work.

- **Once, at startup:** Gateway asks Auth "what's your public key?" and keeps it in memory for as long as it's running. That's the key it uses to tell a genuine Auth-issued token from a forged one.
- **On every request that arrives**, Gateway does the same three checks:
  1. **Where does this go?** It checks the URL against a short internal list — anything under `/auth/` goes to Auth service, `/items/` goes to Items service, `/board/` goes to Board service, `/connectors/` goes to Connectors service. No match, no forwarding — Gateway just says "not found."
  2. **Does this need a login?** A short list of things are allowed without one — signing up, logging in, refreshing, logging out. Everything else needs a valid access token attached. If it needs one and there isn't one (or it's fake/expired), Gateway rejects the request on the spot — it never even reaches the real service.
  3. **Forward it.** If it passes both checks, Gateway repackages the request — same method, same body, same token — sends it to the real service, waits for the answer, and relays that answer straight back. From the outside it looks like you talked to Auth or Items directly; you never actually did.
- **The one exception to "does this need a login":** Connectors' sync endpoint doesn't use a login token at all — it uses a push token, a completely different kind of credential Gateway has no way to check (it only knows how to recognize Auth's own wristbands). So for that one specific kind of request, Gateway steps aside entirely and lets Connectors do its own check instead — not because the request is unprotected, but because Gateway genuinely isn't the right place to protect it.

**Concrete example:** you call Gateway's `/auth/me` with a valid access token. Gateway sees `/me` isn't on the "no login needed" list, checks your token against the public key it fetched at startup, confirms it's real and unexpired, then quietly forwards the same request to Auth's own `/me` endpoint, gets your user info back, and hands it to you. Send a fake token instead, and Gateway catches it itself — confirmed by checking Auth's own logs and seeing that request never arrived there at all.

- **Letting a web page talk to it at all:** a browser won't let a webpage read a response from a different origin (a different port counts) unless the server says "this specific page is allowed to." Gateway says exactly that for the web UI's own address — anything else asking, from a browser, still gets silently blocked by the browser itself before Gateway's answer is ever even shown to it. The browser extension needs this too, just phrased slightly differently: Chrome exempts an installed extension's own pages from this check entirely, but Firefox doesn't — it still asks Gateway's permission the same way a website would — so Gateway also explicitly allows any installed extension's address, in either browser.

## Items service

Items is the catalog of every bookmark you've ever saved, from every source, in one normalized shape — the thing the dashboard actually reads from.

- **Adding a bookmark ("ingest"):** send Items one bookmark's details — where it came from, its title, its URL, when it was saved — and it gets saved under an account. This is the one place Items accepts *either* kind of credential. Show up with your own login wristband, and it saves the bookmark under you, full stop — no way to say whose it is, because it's obviously yours. Show up with a *service* wristband instead (a background sync job acting on nobody's login session), and Items has no idea whose bookmark this is just from the wristband — so the request has to say so explicitly, and Items refuses to guess. If you send the *exact same* bookmark again — same source, same original ID — Items recognizes it's already there and just hands back what it already has, instead of complaining or making a duplicate. That matters because syncing is supposed to happen over and over; re-seeing something you already saved is normal, not an error.
- **Browsing your bookmarks ("list"):** ask Items for everything you've saved, optionally narrowed to just one source (just Twitter, just Chrome). It only ever shows you *your own* items — there's no way to ask for someone else's, and a service wristband doesn't work here at all, since "your own items" only means something for an actual person.
- **Opening one specific bookmark ("get"):** ask Items for one item by its ID. If it's yours, you get it. If it doesn't exist, or it exists but belongs to someone else, you get the exact same "not found" response either way — Items never confirms or denies that another person's bookmark exists.
- **Checking tokens itself, independently:** Items doesn't trust Gateway's word that a request is authorized — it fetches Auth's public key on its own at startup and re-checks every token itself. If Gateway somehow got bypassed, Items would still refuse a bad request on its own.

## Board service

Board is where a curated collection of bookmarks lives, ready to be shared with someone else.

- **Creating a board:** give it a name, and it makes a new board owned by you. Nothing fancy — just a name and an owner.
- **Adding an item to a board:** you point at one of your own items (by ID) and Board attaches it. Behind the scenes, Board actually asks Items "is this really this person's item?" before attaching it — using your own login token, the same way you'd ask directly — so nobody can sneak someone else's bookmark onto their board. When it attaches the item, Board also copies over the display details (title, link, little icon) right then, rather than asking Items again every time someone looks at the board later. Add the same item twice and nothing breaks — you just get back what's already there.
- **Viewing a board:** Board checks whether you're allowed to see it at all — either you own it, or you've accepted an invite to it — and if so, hands back the board's name plus every item on it, using the copies it already has. It never has to go ask Items again just to show you a board. If you have no access, or the board doesn't exist, you get the exact same "not found" either way — same reasoning as Items not confirming another person's bookmark exists.
- **Removing an item:** only the owner can do this. It's forgiving — asking to remove something that's already gone just quietly succeeds, rather than complaining.
- **Inviting someone:** the owner picks an email and Board hands back a one-time link (a random, unguessable code — there's no real email-sending in this project yet, so *something* has to carry that link to the recipient manually for now). Whoever created it stays a "viewer" — there's no picker for other roles yet.
- **Accepting an invite:** whoever is logged in and shows up with that link gets viewer access — Board doesn't check that it's specifically the person the owner intended to share with, the same way a Google Docs "anyone with the link" share works. The first person to actually use the link is the one it sticks to, though — if someone else later gets hold of the same link, it won't work for them anymore. And accepting isn't a separate step you have to think about: the same call that accepts the invite also hands you the board right then, so you land straight on it.
- **Being a viewer:** you can see the board and everything on it, same as the owner. You cannot add or remove items, or invite anyone else — those come back as "not allowed," not silently ignored.

**Why Board keeps its own copy of the item details, instead of asking Items live every time someone looks at a board:** the original plan was for Board to call Items on the spot whenever someone views a board. But Items only ever answers "what are *your* items," scoped to whoever's asking — which works great for the owner, but breaks the moment someone else (a person the board was shared with) tries to view it, since they're not asking about their *own* items. Rather than build a whole separate way for services to vouch for each other, Board just keeps its own snapshot of what it needs to display, taken at the moment the owner added the item. The trade-off: if the original bookmark's title changed later at the source, the board's copy wouldn't know — a real cost, but a small one right now, since nothing in this project updates a bookmark after it's first saved anyway.

## Connectors service

Connectors is the bridge between an actual bookmark source (a browser, or — as of the OAuth handshake, though not the actual bookmark-fetching yet — Twitter/X) and Items' catalog — the thing that actually gets your real bookmarks into the system in the first place.

- **Setting up a browser connection:** you log in with your real account once, and Connectors creates a record — "this browser is now connected to your account" — and hands back a one-time secret, a **push token**, meant for that browser extension alone to keep. Your real login is never needed for this again; from now on, the extension proves itself with just that token.
- **Connecting Twitter — different mechanism, since it's not our own login:** clicking "Connect Twitter" sends you to a real X sign-in and consent screen (not this app's login) — you're proving your identity *to X*, and approving that this app may read your bookmarks. Two secrets have to survive that round trip to X and back: one that only lets the *real* app (not an impostor) complete the exchange at the end, and one that says which of our own accounts asked for this in the first place — both held briefly, server-side, and thrown away the moment they're used. When you land back here, Connectors has a real access token for your Twitter account, stored the same way a browser connection's push token is (never handed back to you again once issued). **What this doesn't do yet:** actually fetch your bookmarks — that's a separate, deliberately deferred step, since (unlike authorizing) it costs real money per bookmark read.
- **Why not just have the extension use your real login every time:** a browser extension runs in a much less trustworthy place than a server — it's sitting in your browser, alongside every other extension you've installed. If it leaked your actual login, whoever got it could do *anything* your account can do. A push token is much narrower — it can only push bookmarks for that one connection, nothing else, and can be thrown away and replaced without touching your real password.
- **Syncing bookmarks:** the extension gathers a whole batch of bookmarks at once (imagine your entire existing Chrome bookmarks folder, not one at a time) and sends them all in a single request, along with its push token. Connectors checks the token against the right connection, then processes several bookmarks in parallel while limiting how many it handles at once, and hands each one to Items. If one bookmark in a batch of two hundred is malformed, that's reported as one failure — the other hundred and ninety-nine still go through. Sending the exact same bookmark again later (a routine re-sync) is a normal, harmless outcome, not an error.
- **Talking to Items on your behalf:** Connectors isn't logged in as you, and it isn't a person at all — so instead of a login token, it holds its own separate machine credential (see Auth's "authenticating a service" note above) and uses that to tell Items "this bookmark belongs to this specific person," even though nobody is sitting at a keyboard for this to happen.

## Web UI

The web UI is the actual website — sign in, see your bookmarks, share a board — as opposed to the browser extension (which only ever does one thing: push your bookmarks in).

It's built as three layers, each one only trusting the layer directly below it:

1. **A thin layer that talks to Gateway** — the only part of the whole app that actually makes network calls. Every other piece goes through it instead of calling Gateway directly. It's also where your tokens physically live, and it's the one place that knows how to quietly get you a new short-lived token when the old one expires, without you noticing.
2. **A single shared "am I logged in?" flag**, sitting above every page. Nothing below it figures out login state on its own — everything just reads this one flag.
3. **The pages themselves, plus a gatekeeper in front of the ones that require being logged in.** The gatekeeper checks layer 2's flag before a protected page is even allowed to render; if you're not logged in, you're redirected to the sign-in page instead.

That layering is what makes each piece replaceable without touching the others — swap out how tokens are refreshed, and no page has to change; add a second protected page later, and it inherits the same gate for free.

- **Signing in:** you type your email and password, the page hands them to Auth (through Gateway, same as everything else) and gets back the same wristband/ticket-stub pair described above. Both get tucked away in the browser's own storage for that site, so the page remembers you're signed in even if you close the tab and come back later.
- **Staying signed in:** every time the page loads, it just checks "is a wristband sitting in storage?" If yes, you're treated as signed in immediately — no extra round-trip to Auth just to confirm. If your wristband quietly expires while you're actively using the site, the page notices on the very next thing it asks for, fetches a new one behind the scenes using your ticket stub, and retries — you never see that happen unless your ticket stub has *also* gone bad (30 days idle, or already used once — see Auth's refresh note above), in which case you're dropped back to the sign-in page.
- **Not repeating the "are you signed in" check on every single page:** pages that require being signed in are grouped together and share one single check. If you're not signed in and try to reach one, you're redirected to the sign-in page instead of that page trying (and failing) to load your data.
- **Signing out:** the page tells Auth to kill your ticket stub for real (not just forgetting it locally — an actual server-side revocation, the same one described above), then forgets both pieces it was holding and sends you back to the sign-in page. If telling Auth fails for some reason (you're offline, say), you still get signed out locally regardless — you're never stuck looking signed-in with no way out.
- **Browsing your bookmarks:** the dashboard fetches everything you've saved once, then splits it into two blocks. Twitter is a flat grid of tiles (no folders — tweets were never organized into anything), with a "Connect Twitter" button next to it — **the block itself will still be empty even after connecting**, since connecting only proves you own the Twitter account and gets a token; actually pulling your bookmarks in is a separate, not-yet-built step (Twitter reads cost real money, unlike the connection itself). Browser Bookmarks rebuilds your browser's actual folder structure from a flat list of "this bookmark lives at path X" records, and shows it as a click-to-expand tree — everything starts collapsed, so you're not staring at hundreds of bookmarks the moment the page loads.
- **Selecting bookmarks to share:** every tile and every bookmark row has a checkbox. You can check them one at a time, or hit "Select all" and uncheck the few you don't want — either way works, since it's the same underlying selection either way.
- **Sharing a selection:** once something's selected, "Share selected" walks you through naming a new board and typing the recipient's email, then does three things in order: creates the board, copies each selected bookmark's display details onto it (a snapshot, not a live link back to your account — see Board's own section above), and creates a one-time invite. There's still no real email-sending in this project (same as before) — the resulting link is shown right there on screen for you to copy and send yourself.
- **Accepting a shared board:** opening that link while signed out first asks you to sign in (or sign up, if you don't have an account) — and remembers where you were headed the whole time, so right after that you land straight on the shared board, exactly as if you'd clicked a normal link. No separate "accept" button to find or click. From there you can open any of the board's links, same as browsing your own bookmarks, but you can't add, remove, or re-share anything — you're a Viewer.
- **A known, not-yet-built gap:** once you leave a shared board, there's currently no list anywhere of boards you've been given access to, or (if you're the one sharing) who you've shared what with. Getting back to a board right now means still having the original link. This is flagged as a high-priority backlog item — see the architecture doc.
